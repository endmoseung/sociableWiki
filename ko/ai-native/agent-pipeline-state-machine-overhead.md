# 자율 agent 파이프라인의 비용은 상태 기계에서 새어 나갑니다

multi-agent 파이프라인 비용이 커지면 저는 먼저 모델을 의심합니다. 코드를 엉망으로 짰거나 작업을 잘못 읽었겠거니 합니다. 그런데 제가 본 공개 회고 중 가장 자세한 글은 다른 곳을 가리킵니다. **비싼 실패는 절차의 모양에서 나왔습니다.** agent가 나쁜 코드를 써서가 아니라, 작업 흐름 그래프에 빠진 간선이 있고, 모든 변경에 같은 검사를 걸고, 빠져나갈 출구가 없는 루프가 있어서 생긴 실패였습니다.

## 사례

Cockroach Labs는 2026년 4월부터 9월까지 **MOLT Sinai**를 운영했습니다. 라벨로 움직이는 GitHub Actions 파이프라인인데, 수련 병원을 본떠 만들었습니다. issue는 "환자"이고 병합은 "퇴원"입니다. 역할은 분류(triage), 구현을 맡는 전임의(fellow), 리뷰를 맡는 담당 교수, 절차를 감사하는 퇴원 간호사, 막힌 작업을 정리하는 책임 간호사, 그리고 감염 관리, 안전, 연구 역할이 있습니다. 각 단계는 issue에 정해진 형식의 기록을 남기고 다음 라벨을 붙입니다. 반려되면 작업이 앞 단계로 돌아갑니다.

회사가 직접 발표한 수치입니다(회사 블로그 기준이며 외부 검증은 받지 않았습니다).

| 항목 | 값 |
|---|---|
| 병합한 PR / 반영한 코드 줄 수 | PR 1,238개 / 100만 줄 이상 |
| 파이프라인이 작성한 커밋 비율 | 약 1,570개 중 약 85% |
| 전체 토큰 비용 | 약 13만 5천 달러, issue당 약 84달러 |
| 계획 리뷰 반려율 | 10% 미만 |
| 큰 기능 하나(Db2 지원) | 2일 미만, 하위 issue 32개, 재작업 55회, 상위 보고 9회(사람에게 2회), 4,172달러 |

## 실패는 그래프 안에 있었습니다

| 보고된 증상 | 상태 기계 안의 원인 |
|---|---|
| 중복 issue를 닫는 일이 사람에게까지 올라왔습니다 | "수정 불필요"라는 종료 상태가 없었습니다. 갈 간선이 없는 결과는 상위 보고 간선으로 떨어집니다. |
| 한 줄짜리 문구 수정에 재작업이 5번, 다른 한 줄 수정에는 11번 돌았습니다 | 모든 변경이 같은 리뷰 경로를 지나서, 변경 크기나 위험도에 따라 리뷰 강도가 달라지지 않았습니다. |
| 복잡한 issue 3개가 1,046달러 예산 구간 중 약 631달러를 썼습니다 | 리뷰와 수정을 오가는 루프에 수렴 여부를 보는 장치가 없었습니다. |
| 절차 감사 역할이 실행할 때마다 약 2만 9천 토큰의 지시문을 읽었고, 역할 지시문 약 10만 단어 중 23%는 지워도 어떤 검사 결과도 바뀌지 않았습니다 | 지시문은 역할마다 불어나고, 상태가 바뀔 때마다 그 비용을 냅니다. |
| 연구 역할이 제안을 쏟아내 대기열을 채웠습니다 | 생산 노드에 역압(back-pressure)이 없었습니다. |

## 구조로 고치는 방법

1. **모든 결과에는 간선이 있어야 합니다.** 종료 상태를 미리 나열합니다. 수정 완료, 중복, 수정 안 함, 정보 필요, 더는 해당 없음, 분할 같은 것들입니다. 나열하지 않은 결과는 상위 보고로 흘러가고, 그건 그래프에서 가장 비싼 간선입니다.
2. **단계가 아니라 변경 위험도로 경로를 정합니다.** 오타 하나와 데이터 경로 변경을 똑같이 계획 → 리뷰 → 구현 → 리뷰 → 감사 경로로 보내는 게 바로 "획일적인 검사" 안티패턴입니다. 각 검사의 비용은 그 단계를 되돌릴 수 있는지, 오류가 뒤에서 드러나는지로 매깁니다. *사람* 검토를 어디에 둘지 정할 때 쓰는 기준과 같습니다.
3. **리뷰 루프에 수렴 차단기를 둡니다.** Sinai는 연속 4회 동안 매번 *새로운* 차단 지적이 나오거나, 실질적인 리뷰가 6회를 넘으면 상위로 보고합니다. 전체 횟수가 아니라 *새* 차단 지적을 센다는 점이 핵심입니다. 그래야 "천천히 수렴하는 중"과 "리뷰어가 계속 새 문제를 찾아내는 중"을 구분할 수 있고, 계획이 잘못됐다는 신호는 뒤쪽뿐입니다.
4. **생산자에 상한을 둡니다.** 연구 역할은 3시간마다 돌던 것을 하루 한 번으로 바꾸고, 받아들여지지 않은 제안은 최대 10개까지만 쌓이게 했습니다. 일을 만들어 내는 agent에는 대기열 한도가 있어야 합니다. 그렇지 않으면 파이프라인이 자기 예산을 스스로 먹어 치웁니다.
5. **역할별 지시문을 검사 결과와 대조해 감사합니다.** 문단 하나를 지워도 어떤 검사의 판정도 바뀌지 않는다면, 그 문단은 실행할 때마다 나가는 비용일 뿐입니다.

## 가져다 쓸 만한 장치

- **상위 보고를 줄이는 선례 기록.** 사람이 상위 보고 건을 판정했는데 그 판정이 일반화된다면 기록에 남기고, agent는 상위 보고 전에 이 기록을 먼저 확인해야 합니다. 사람의 결정이 재사용할 수 있는 판례가 됩니다. 실행이 끝날 때 결정할 일을 한데 모아 보고하는 방식과도 잘 맞습니다. 모아 보고하는 쪽은 새 결정을 받고, 선례 기록은 이미 내린 결정이 다시 올라오지 않게 막습니다. 다만 원래 범위 밖에 선례를 적용하면 아무도 모르게 틀린 결정이 내려집니다. 판정마다 적용 범위를 옆에 적어 두세요.
- **절차 기록은 코드 브랜치 밖에 둡니다.** 계획, 리뷰, 인계, 단계별 비용은 별도 보관용 브랜치에 남기고 PR diff에는 코드만 남깁니다. 리뷰어의 context를 부풀리지 않고도 감사 기록을 지킬 수 있습니다.
- **인계 내용을 다시 말하게 합니다.** 막힌 agent는 정해진 형식으로 인계 기록을 쓰고, 넘겨받은 쪽은 작업 전에 그 내용을 자기 말로 **다시 말해야** 합니다. 인계가 전달만 된 게 아니라 이해됐는지 싸게 확인하는 방법입니다.
- **리뷰는 테스트를 증명하는 데서 시작합니다.** 리뷰어는 수정을 판단하기 전에 변경을 되돌려 새 테스트가 실패하는지부터 확인합니다.

## 이 글이 맞지 않는 경우

- **규모가 작으면 상태 기계 자체가 비용입니다.** 하루에 agent 작업을 몇 건 돌리는 정도라면 역할 9개짜리 그래프보다 계획 확인과 테스트 검사를 갖춘 세션 하나가 낫습니다. 위의 구조적 실패는 issue가 수백 건 단위일 때 비로소 비용을 좌우합니다.
- **처리량은 검증된 품질이 아닙니다.** Cockroach Labs도 직접 밝혔듯 Db2 코드는 자율 실행 중에 리뷰를 거치지 않았고, 사람 승인 모드는 그 뒤에 켰습니다. 위 수치는 생산량을 말할 뿐 정확성을 말하지 않습니다.
