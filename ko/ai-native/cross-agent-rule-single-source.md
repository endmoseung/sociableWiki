## 한 줄 요약

저는 코딩 에이전트 두 개(Claude Code, Codex)를 함께 쓰고, 둘 다 같은 개인 규칙을 따르게 하고 싶었습니다. 사본 두 벌을 따로 고치면 내용은 저절로 어긋납니다. 제 경우도 그랬습니다. 이 문제를 푼 구성은 두 부분입니다.

1. **원본 한 벌을 두고 각 도구의 규칙 폴더에 심볼릭 링크로 연결합니다.** 하드링크는 쓰지 않습니다. 파일을 새로 쓰는 편집기는 하드링크를 소리 없이 끊지만, 심볼릭 링크는 그대로 남거나 원본을 고치도록 유도합니다.
2. **링크를 복구하고 모순을 찾는 작업을 매일 돌립니다.** 어떤 도구가 링크를 일반 파일로 바꿔 놓았으면 3방향 병합으로 되살리고, LLM 판정자에게 동시에 지킬 수 없는 규칙 쌍을 찾게 합니다. 이긴 쪽 문장을 뒷받침하는 사람의 지시를 그대로 인용할 수 있을 때만 자동으로 고칩니다.

## 발단

2026년 9월 기준으로 Claude Code는 프로젝트에 `CLAUDE.md`가 없으면 `AGENTS.md`를 대신 읽기 시작했습니다. 제 홈 디렉터리에는 `CLAUDE.md`가 없었기 때문에, 두 달 동안 손대지 않은 328줄짜리 `~/AGENTS.md`가 최신 규칙과 함께 조용히 로드되고 있었습니다. 같은 무렵, 공통 규칙 모듈 7개 중 5개가 Claude 사본과 Codex 사본 사이에서 서로 달라져 있다는 것도 알게 됐습니다. 누가 실수한 것은 아니었습니다. 그냥 사본 두 벌을 따로 고쳐 왔을 뿐입니다.

두 문제는 모양이 같습니다. 죽었거나 맞춰져 있다고 생각한 파일이 실제로는 살아 있었고 내용도 달랐습니다.

## 구성

| 층 | 위치 | 누가 읽나 |
|---|---|---|
| 공통 모듈 7개 | 두 도구의 설정 폴더 밖에 둔 원본 디렉터리 하나 | 두 도구 모두. `~/.claude/rules/`와 `~/.codex/rules/`의 심볼릭 링크로 연결합니다 |
| 도구 전용 규칙 | 도구마다 파일 하나 | 해당 도구만 |
| 색인 | `~/.claude/CLAUDE.md`, `~/.codex/AGENTS.md` | 해당 도구만 |
| 홈 안내 | `~/AGENTS.md`, 위 파일들을 가리키기만 하는 10여 줄로 줄임 | 홈에서 실행할 때 두 도구 모두 |

규칙끼리 부딪힐 때의 우선순위는 공통 규칙 안에 따로 적어 두었습니다. 그래야 아래의 판정자가 기준으로 삼을 것이 생깁니다.

## 심볼릭 링크를 고른 근거(직접 측정)

어떤 링크가 나은지 짐작하지 않고, 실제 편집 도구로 하나씩 확인했습니다(2026년 9월 기준).

- **Claude Code의 Edit 도구는 심볼릭 링크 경로로는 쓰기를 거부하고** 원본 경로로 쓰라고 안내합니다. 결과적으로 원본만 바뀝니다. 바라던 동작입니다.
- **Claude Code의 Edit 도구는 하드링크를 끊습니다.** 새 inode로 파일을 쓰기 때문에, 연결돼 있던 파일이 소리 없이 독립된 사본이 됩니다. Claude가 고칠 수 있는 파일에는 하드링크를 쓰면 안 됩니다. 저는 그동안 skill 파일을 관례처럼 하드링크로 묶어 왔는데, 같은 위험을 안고 있었습니다.
- **Codex의 `apply_patch`는 심볼릭 링크 경로로 고쳐도 링크를 유지합니다.**
- **전역 `CLAUDE.md`의 `@` import는 심볼릭 링크를 따라갑니다.** 반면 *프로젝트* `CLAUDE.md`에서 프로젝트 폴더 밖을 가리키는 import는 로드되지 않았습니다.
- **예전에 쓰던 사본 동기화 도구는** 두 경로가 같은 파일을 가리키자 `SameFileError`로 멈췄습니다. 그래서 그 도구의 목록에서 규칙 파일 쌍을 뺐습니다. 동기화 도구와 링크는 같은 문제에 대한 두 가지 답이니 하나만 남깁니다.

## 매일 도는 검사

예약 작업이 하루에 한 번 실행됩니다. 컴퓨터가 잠들어 있었다면 깨어난 뒤에 실행합니다.

1. **링크 복구.** 어떤 도구가 링크를 일반 파일로 바꿔 놓았으면, 마지막으로 맞춰 둔 기준 사본과 3방향 병합을 합니다. 한쪽만 바뀌었으면 그 변경을 원본에 반영하고 링크를 되살립니다. 같은 곳을 양쪽이 다르게 고쳤으면 추측하지 않고 결정 카드를 만듭니다.
2. **모순 판정.** 감시하는 파일이 바뀐 날, 그리고 그와 상관없이 일주일에 한 번, LLM 판정자가 전체 규칙을 읽고 동시에 지킬 수 없는 문장 쌍을 찾습니다. 판정자는 `claude -p --safe-mode --tools "" --no-session-persistence`로 격리해 실행합니다. 그래서 `CLAUDE.md`, hook, 도구가 모두 꺼지고 세션 기록도 남지 않습니다. 판정자가 인용한 문장이 파일에 글자 그대로 없으면 그 쌍은 버립니다.
3. **근거 찾기.** 모순마다 먼저 그 파일을 마지막으로 고친 세션을 찾아, 수정 직전에 **사람이 직접 입력한 메시지**만 읽습니다. subagent에게 전달된 지시문과 도구 출력은 에이전트가 스스로 쓸 수 있는 글이라 제외합니다. 세션에서 근거를 찾지 못하면 개인 노트를 검색합니다.
4. **처리.** 사람의 지시나 노트 문장을 글자 그대로 인용할 수 있고, **동시에** 진 쪽 문장이 실제로 지워질 때만 자동으로 고칩니다. 파일 수정은 스크립트가 하고, LLM은 JSON만 돌려줍니다. 나머지는 모두 결정 카드로 남기고, 두 도구의 세션 시작 hook이 열린 카드 수를 알려 줍니다.

## 성능에서 배운 점

세션 기록이 꽤 컸습니다(Claude 약 1.4GB, Codex 약 6.5GB). BSD grep에 고정 문자열 패턴을 여러 개 주어 훑었더니 CPU 시간이 약 50분 걸렸고, 로케일을 `C`로 바꿔도 같았습니다. 편집 기록에 공통으로 붙는 접두어(`"file_path":`, `Update File: `)를 Python 정규식으로 찾고 파일 수정 시각 기준으로 캐시했더니, 첫 색인은 31초, 그 뒤로는 실행마다 3.7초가 걸렸습니다.

함정이 하나 있습니다. Codex는 턴마다 규칙 파일을 다시 읽기 때문에, **경로**로 검색하면 거의 모든 세션이 걸립니다. **편집 기록 문자열**로 검색해야 합니다.

## 알려진 한계

- 판정자가 놓친 모순은 그대로 남습니다. 일주일마다 도는 전체 감사가 그중 일부를 잡습니다.
- 세션 기록은 두 달 정도만 남아 있어서, 오래전에 고친 규칙은 세션에서 근거를 찾지 못하고 노트 검색으로 넘어갑니다.
- "이번 세션 정리해 줘" 같은 묶음 작업으로 규칙을 한꺼번에 고치면, 수정 직전 사람 메시지가 그 한 문장뿐이라 근거로 쓸 수 없습니다. 묶음 수정은 감사 기록을 약하게 만듭니다.

## 이 판단이 틀리는 경우

에이전트 도구를 하나만 쓰거나, 두 도구에 정말로 다른 규칙이 필요하다면 원본을 하나로 묶어 봐야 링크 관리 부담만 늘어납니다. 그때는 파일을 따로 두고 어긋남을 감수하는 편이 낫습니다. 또 도구의 편집기가 심볼릭 링크를 다루는 방식이 바뀌면 다시 측정해야 합니다. 위의 링크 선택은 마지막으로 확인한 시점까지만 유효합니다.
