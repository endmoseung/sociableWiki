# 실행 끝 보고서는 결정 대기열이고, 말없이 정한 가정이 새는 구멍입니다

## 한 줄 요약

Anthropic이 2026년 10월에 낸 Claude Code용 Opus 5.5 활용 가이드에는 조언 두 개가 나란히 나옵니다. 하나는 CLAUDE.md에 넣는 규칙으로, 정말 막혔거나 되돌릴 수 없는 작업 직전이 아니면 멈추지 말고 계속 진행하라는 내용입니다. 다른 하나는 읽는 요령으로, 최종 요약에서 "needs from you" 부분부터 읽으라는 조언입니다.

저는 이 둘을 따로 떨어진 팁이 아니라 하나의 설계로 봅니다. 계속 진행하라는 규칙은 사람이 내릴 결정을 없애지 않습니다. **막히지 않는 결정을 실행 끝으로 미뤄서 한꺼번에 묶을** 뿐입니다. 그러면 최종 보고서는 진행 상황 요약이 아니라 사람이 처리할 **결정 대기열**이 됩니다.

가이드가 말하지 않은 구멍이 하나 있습니다. 막히지 않은 선택을 지나쳐 계속 가려면 에이전트는 뭔가를 골라야 합니다. 그 선택이 보고서에 올라오지 않으면 결정은 조용히 내려진 것이고, 사람은 되돌릴 기회조차 갖지 못합니다.

(실행 자체를 어디서 끊고 어떻게 다시 이어 갈지는 별개 주제입니다. 이 글은 실행 끝 보고서에 무엇이 실려야 하는지만 다룹니다.)

## 계속 진행 규칙에서 사람의 결정은 어디로 가는가

```
수시 확인 방식                         계속 진행 방식
──────────────────────                ─────────────────────────────────────
단계 → 질문 → 대기 → 단계 → 질문       단계 → 단계 → (가정) → 단계 → … → 보고
사람이 중간중간 N번 결정               사람이 보고서를 보고 한 번에 결정
```

긴 실행에는 결정이 필요한 순간이 세 종류 있습니다.

| 순간 | 에이전트의 행동 | 사람이 보는 곳 |
|---|---|---|
| 막힘(더 진행할 수 없음) | 멈추고 묻습니다 | 실행 중 질문 |
| 파괴적 작업(삭제, force-push, 저장소 밖 작업) | 멈추고 묻습니다 | 실행 중 권한 확인 |
| 막히지 않은 선택(이름, 대체 방법, 범위 경계) | **기본값을 골라 계속 갑니다** | 최종 보고서. *에이전트가 적어 둔 경우에만* |

바뀐 건 세 번째 줄입니다. 예전에는 작업을 끊고 묻던 순간이었는데, 이제는 에이전트가 대신 고른 기본값이 됩니다. 그 선택을 되돌릴 수 있는 곳은 보고서밖에 없습니다.

## "needs from you"만으로는 왜 새는가

"needs from you"에는 에이전트가 *아직 열려 있다고 아는* 항목만 올라옵니다. 이미 스스로 정해 버린 선택은 에이전트에게 더 이상 열린 문제로 느껴지지 않습니다. 그런데 계속 진행 규칙이 새로 만들어 낸 결정이 바로 이런 종류입니다. 가정으로 처리한 항목은 에이전트가 그것을 결정으로 느끼지 않게 된 바로 그 이유 때문에 대기열에서 빠집니다.

subagent가 돌려주는 요약이 자기 보고에 불과하다는 문제와 구조가 같습니다. 다만 이번에는 그 보고를 사람이 받습니다. 보고서가 빠짐없는지는 에이전트 본인의 진술에 달려 있습니다. "꼼꼼하게 써 줘"라고 부탁해서는 고쳐지지 않습니다. 가정에 이름 붙은 칸을 따로 줘야 합니다. 그래야 빠뜨렸을 때 눈에 보이는 누락이 됩니다.

## 계속 진행 규칙 옆에 두는 보고 형식

저는 보고서 형식을 계속 진행 규칙과 같은 CLAUDE.md 블록에 둡니다. 순서는 놓쳤을 때 제가 치를 비용이 큰 것부터입니다.

```
긴 실행이 끝나면 아래 순서로 보고합니다.
1. 내가 결정할 것: 나만 정할 수 있는 결정. 답이 없을 때 적용할 기본값을 함께 적습니다.
2. 묻지 않고 정한 가정: 막히지 않은 선택마다 무엇을 골랐고 어떻게 되돌리는지 적습니다.
3. 검증하지 못한 것: 바꿨지만 증명하지 못한 것(테스트·실행·재현 없음).
4. 완료한 것: 바뀐 내용과 증거(테스트 출력, file:line).
```

- **2번이 구멍을 막습니다.** 말없이 정한 기본값을 검토할 수 있는 항목으로 바꿉니다.
- 1번의 **"답이 없을 때 적용할 기본값"** 덕분에 대기열을 한동안 안 읽어도 안전합니다. 그렇다고 무시해도 된다는 뜻은 아닙니다.
- **3번은 "완료"를 정직하게 지킵니다.** 증명하지 못한 변경이 성공 목록에 섞여 숨지 못합니다.
- **"완료"를 일부러 마지막에 둡니다.** 제게 가장 덜 필요한 부분이고, 에이전트가 실행 중에 이미 충분히 알려 준 내용입니다.

문구보다 순서가 더 중요합니다. 보고서가 긴 성공 요약으로 시작하면 저는 대충 훑게 되고, 정작 제가 봐야 할 두 칸도 함께 훑고 지나갑니다.

## 이 규칙이 틀리는 경우

- **짧고 대화형인 실행.** 답을 하나하나 읽고 있다면 중간에 묻는 비용은 거의 없고, 보고 형식은 순수한 부담이 됩니다.
- **가정 목록이 비대해질 때.** 2번에 사소한 항목이 수십 개 쌓이면 저는 그 칸도 훑기 시작하고, 대기열은 원래 대체하려던 안 읽히는 요약으로 돌아갑니다. 동작이나 공개 접점(API 형태, 다른 코드가 import하는 파일 이름, 사용자에게 보이는 문구)을 바꾸는 선택만 남깁니다.
