# 검증 안 된 agent 테스트는 역효과를 냅니다 — fail-on-base부터 확인하세요

예전에 저는 agent가 쓴 테스트를 *약한* 근거 정도로 여겼습니다. 동어반복일 수는 있어도 나빠 봐야 해는 없고, 테스트가 많을수록 좋다고 생각했습니다. 2026년 9월에 나온 논문은 반대 결과를 보여 줬습니다. 훈련하지 않은 테스트 작성 agent의 테스트를 보고 수정 agent가 움직이자, SWE-bench Verified 해결률이 **테스트를 아예 안 줬을 때보다 낮아졌습니다.** 61.2%에서 57.3%로 떨어졌습니다. 반대로 맞는 패치와 틀린 패치를 구분하는 테스트를 쓰도록 테스트 agent를 훈련하고, 실패하면 막는(fail-closed) harness가 그 테스트를 검증하고 고정한 뒤에 수정 agent에게 넘기자 같은 파이프라인이 72.6%에 도달했습니다. 테스트가 없을 때보다 11.4%p 높은 수치입니다(Tao 외, arXiv 2609.09133).

결국 피드백이 도움이 될지 해가 될지는 테스트 품질이 정합니다. 검증하지 않은 테스트는 "신호가 조금 약한" 정도가 아닙니다. **수정 루프가 최적화하며 따라가는 잘못된 목표**입니다.

## 왜 역효과가 나는가

추론 과정을 단계별로 보면 이렇습니다.

1. 수정 루프는 "테스트 통과"를 멈춤 조건으로 씁니다. 초록불이 될 때까지 고칩니다.
2. 버그가 있는 코드에서 이미 통과하는 테스트는 루프에 너무 이른 초록불을 줘서 일찍 멈추게 합니다. agent가 issue를 잘못 이해한 내용이 담긴 테스트는 루프가 그 잘못된 이해 쪽으로 "고치게" 만듭니다.
3. 어느 쪽이든 루프는 확신을 갖고 틀린 패치에 도달합니다. 피드백이 아예 없었다면 모델이 최소한 issue 본문을 보고 추론해야 했을 겁니다.
4. 그래서 확인하지 않은 테스트는 신호가 0으로 희석되는 데서 끝나지 않습니다. 루프를 특정한 틀린 방향으로 밀어 줍니다.

## 검증 단계: 의미를 몰라도 기계적으로 됩니다

agent 테스트를 두고 보통 두 가지를 묻습니다. *정답 기준(oracle)이 어디서 왔는가*, 그리고 *누가 테스트를 고칠 수 있는가*. fail-on-base 검사는 그 둘 사이에 들어가는 값싼 기계적 단계입니다. agent가 쓴 회귀 테스트가 루프를 이끌거나 PR의 근거로 인정받으려면 먼저 아래를 통과해야 합니다.

| 검사 | 실행 대상 | 기대 결과 | 아니라면 |
|---|---|---|---|
| Fail-on-base | 부모 커밋(소스는 되돌리고 새 테스트는 유지) | **빨간불** | 이 테스트는 이번 버그에 대해 아무것도 증명하지 못합니다. 근거에서 뺍니다. |
| Pass-on-fix | 패치를 적용한 코드 | 초록불 | 평범한 실패입니다. 수정을 계속합니다. |
| 고정 | 검증을 마친 뒤 | 수정 agent에게는 읽기 전용 | 그렇지 않으면 agent가 테스트를 패치에 맞춰 고칠 수 있습니다. |

양쪽 코드에서 모두 초록불인 테스트는 동어반복 테스트를 바깥에서 본 모습입니다. 단언문을 읽어 보지 않아도 이번 변경에 대한 정보가 없다는 걸 알 수 있습니다. 정적인 방법도 있습니다. 테스트에 동어반복, 특성화(characterization), 실패 경로, 속성 같은 라벨을 붙이고, 운영 코드는 늘었는데 동어반복 테스트만 추가됐으면 병합을 거부하는 식입니다. fail-on-base는 이를 동적으로 하는 방법이고, 라벨도 분류기도 의미 판단도 필요하지 않습니다.

PR 검사로 쓴다면 대략 이런 모양입니다.

```bash
# PR에서 새로 추가하거나 바꾼 테스트를 base 커밋의 소스로 실행합니다.
git checkout origin/main -- <PR이 건드린 테스트 외 소스 파일>
<새 테스트 실행>                       # 기대: 최소 하나는 실패
git checkout HEAD -- <소스 파일>        # 원상 복구
```

순수한 리팩터링에는 fail-on-base 테스트가 없는 게 정상입니다. 리팩터링의 근거는 새 테스트가 아니라 동작이 그대로라는 특성화 테스트 재실행입니다. 이 검사는 설명에 "회귀 테스트 추가"라고 적은 버그 수정 PR과 기능 PR에 적용합니다.

## 제가 적용하는 방식

- **리뷰에서는** fail-on-base를 보여 줘야만 회귀 테스트를 근거로 인정합니다. CI 로그든 로컬 실행 결과를 붙인 것이든 상관없습니다. "테스트 추가했고 통과함"만으로는 근거가 되지 않습니다.
- **자율 수정 루프에서는** 테스트 작성과 수정 작성 *사이에* fail-on-base 검사를 넣습니다. TDD에도 빨간불 단계가 있지만, 루프가 그 빨간불을 직접 *관찰*해야 합니다. 빨간불이었다는 agent의 말을 그대로 믿으면 안 됩니다.

## 이 방법이 맞지 않는 경우

- **base가 빌드되지 않을 때.** 테스트가 새 API를 import하는 경우처럼 부모 커밋이 새 테스트와 함께 컴파일되지 않으면, "빨간불"은 동작 실패가 아니라 컴파일 에러입니다. 이런 테스트는 검증되지 않은 것으로 보고, 기존 인터페이스를 대상으로 쓴 테스트나 예전 진입점을 거치는 동작 단언을 요구하세요.
- **불안정한(flaky) 테스트.** 불안정한 테스트는 우연히 base에서 빨간불이 될 수 있습니다. 빨간불을 믿기 전에 base에서 두세 번 돌려 보세요.
- **역효과 수치는 모델 하나, 벤치마크 하나에서 나왔습니다.** 57.3%는 훈련하지 않은 특정 크기의 모델 하나(Qwen-3.5-35B-A3B)를 SWE-bench Verified에서 돌린 결과입니다. 더 강한 모델이라면 검증 안 된 테스트도 역효과까지는 안 가고 중립에 머물 수 있습니다. 다른 환경에 가져갈 수 있는 건 크기가 아니라 방향, 즉 품질이 도움과 해를 가른다는 점입니다.
