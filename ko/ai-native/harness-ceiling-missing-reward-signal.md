# harness의 천장은 빠진 보상 신호에서 생긴다

harness 작업에는 천장이 있습니다. prompt를 다듬고, 오케스트레이션을 늘리고, 리뷰 agent를 더 붙이면 agent의 결과물이 어느 지점까지는 좋아지다가 거기서 멈춥니다. 저는 이 천장이 실제로 있고, harness로 얻은 이득은 모델마다 다르다는 것까지는 이미 알고 있었습니다. 한 모델에서 조율해 얻은 이득이 다음 모델로 잘 넘어가지 않습니다. 모르던 것은 *애초에 왜 천장이 생기는가*였습니다.

Dex Horthy가 2026년 7월에 내놓은 주장이 그 답을 줍니다. 도구 이야기가 아닙니다. **RL 학습에는 유지보수성을 해치는 데 대한 벌점이 없습니다. 유지보수성을 빠르게 판정할 방법이 없기 때문입니다.** 테스트는 몇 초 만에 통과와 실패를 돌려줍니다. 나쁜 아키텍처의 비용은 몇 주나 몇 달 뒤에야 드러나고, 그때는 학습에 되먹이기에 너무 늦습니다. 그래서 모델은 빠른 판정 기준이 있는 일에는 아주 능숙해지고, 그런 기준이 없는 일에는 무심한 채로 남습니다. 그리고 **학습할 때 없던 보상 신호는 prompt나 오케스트레이터를 아무리 겹겹이 얹어도 생기지 않습니다.**

## 최적화 대상이 뒤집히는 이유

빈틈의 원인이 판정 기준의 부재라면, 코드 생성 *뒤에서* 메울 수는 없습니다. 리뷰어를 늘리고, 비평 agent를 똑똑하게 만들고, prompt를 엄격하게 해도 마찬가지입니다. 메울 곳은 **앞단**입니다. 모델이 그대로 두면 엉뚱하게 해석할 모호함을 미리 없애는 것입니다. 그래서 직관과 반대되는 숫자가 나옵니다. **계획에 30분 정도를 쓰면 리뷰 시간이 몇 시간 줄고**, 안전하게 얻을 수 있는 속도 향상은 "소프트웨어 공장" 홍보가 말하는 10~100배가 아니라 **2~3배 정도**입니다.

이 주장은 "이득이 모델마다 다르다"는 발견을 반복하지 않고 그 위에 겹쳐집니다.

| | "harness 이득은 다른 모델로 넘어가지 않는다" | "천장은 빠진 보상 신호에서 생긴다" |
|---|---|---|
| 주장 | harness 이득은 크지만 모델마다 다릅니다 | 학습 신호가 없어서 천장이 생깁니다 |
| 수준 | 경험적 근거: 이전이 실패한 것을 측정했습니다 | 인과 설명: 왜 그런지 원리를 밝힙니다 |
| 해야 할 일 | 모델마다 harness를 다시 조율합니다 | 노력을 코드 생성 앞단으로 옮깁니다 |

앞의 발견은 harness 작업이 다른 모델로 옮겨 가지 않는다는 것이고, 이 글의 주장은 *어떤* 모델에서도 harness로 살 수 없는 품질이 따로 있다는 것입니다.

## "비평 agent를 붙이면 된다"가 통하지 않는 이유

가장 먼저 떠오르는 처방은 유지보수성을 채점하는 judge agent입니다. 여기에 대한 반론은 자기 자신을 가리킵니다. 모델이 좋은 아키텍처와 나쁜 아키텍처를 믿을 만하게 구분할 수 있다면, 처음부터 좋은 쪽을 썼을 것입니다.

reward hacking과 같은 구조입니다. **평가받을 시스템이 만든 대리 지표는 독립적인 판정 기준이 되지 못합니다.** 비평 subagent도 가장자리에서는 도움이 됩니다. *명시한* 기준은 잡아 주기 때문입니다. 하지만 기반 모델이 한 번도 배우지 않은 품질 신호를 새로 만들어 내지는 못합니다. judge 모델과 mutation testing을 묶어 머지 가능성을 채점하는 Cognition의 FrontierCode는 측정 쪽에서 실제로 진전한 사례지만, 문제가 풀린 것은 아닙니다.

## 근거와 그 무게

정량 근거의 뼈대는 Faros AI가 2026년 1월부터 모은 엔지니어링 지표입니다. 이 수치를 인용할 때는 단서를 꼭 붙여야 합니다. **상관관계일 뿐, 통제된 비교가 아닙니다.**

- 리뷰를 아예 건너뛴 PR이 **31.3%** 늘었습니다.
- 리뷰 댓글은 **25%** 많아졌고 **22.7%** 길어졌습니다.
- PR당 프로덕션 장애는 **242.7%**, 월간 장애는 **57.9%**, 개발자당 버그는 **54%** 늘었습니다.

앞의 두 줄을 같이 읽으면, 리뷰를 건너뛰는 일은 *더 잦아졌고* 리뷰를 하는 곳에서는 리뷰가 *더 무거워졌습니다.* 병목이 코드 생성에서 검증으로 옮겨 갔다는 신호입니다.

가장 유명한 "불 꺼진 공장" 사례에는 공개된 사후 분석이 없고, Hacker News 토론(394점, 댓글 271개)도 의견이 정말로 갈렸습니다. 공장이 실패했다는 이야기는 부분적인 데이터를 곁들인 실무자의 주장으로 받아들이고, 확정된 결과로 다루지 않습니다.

## 루프, harness, 공장

Addy Osmani의 짝이 되는 글은 층마다 깔끔한 이름을 붙였습니다.

| 층 | 무엇인가 | 중요한 기준 |
|---|---|---|
| 루프 | context 모으기 → 행동 → 확인을 조건이 맞을 때까지 반복합니다 | **3~10단계**에서 잘 돌고, 20단계쯤 넘어가면 흐름을 놓칩니다 |
| harness | 샌드박스, 도구, 실행을 넘나드는 메모리, "완료"를 정하는 관문입니다 | 루프를 담는 그릇이고, 모델이 학습한 품질을 넘어서지 못합니다 |
| 공장 | harness를 씌운 루프 여러 개가 작업 대기열을 리뷰 관문으로 흘려보냅니다 | 더 큰 agent가 아니라 "an org chart made of loops"(루프로 만든 조직도)입니다 |

가장 중요한 문장은 이것입니다. **공장의 병목은 생성 능력이 아니라 검증 능력입니다.** 자율성은 싸고 믿을 만하게 검증할 수 있는 범위를 넘어설 수 없습니다. 3~10단계라는 범위는 작업을 쪼갤 때 쓸 실용적인 예산이기도 합니다. 20단계를 넘어가면 루프를 늘리지 말고 작업을 나눕니다.

## 할 일: 사후 확인보다 앞단에 몰아 두기

권장 구조는 구현 *전에* 거치는 네 단계입니다. 단계마다 모델이 짐작으로 채웠을 결정을 한 부류씩 없앱니다.

1. **제품 리뷰(30분 정도)** — 목업과 성공 지표로 사용자가 겪을 경험을 확정합니다.
2. **시스템 아키텍처** — 시퀀스 다이어그램과 계약으로 구성 요소가 어떻게 주고받는지 정합니다.
3. **프로그램 설계** — 코드보다 먼저 타입, 시그니처, 파일 트리, 호출 스택을 정합니다.
4. **수직 조각** — 층별로 쌓지 않고 끝에서 끝까지(저장소 → 서비스 → API → UI) 만들며, 단계 사이마다 테스트합니다.

작업 크기에 따라 나눠 적용해야 형식적인 절차가 되지 않습니다. **작업의 약 40%는 여전히 agent에게 한 번에 맡길 만합니다.** 중간 크기 작업은 제품 리뷰와 아키텍처까지만 거치고, 큰 기능만 네 단계를 모두 밟습니다. 모든 작업에 네 단계를 다 적용하면 계획이 군살처럼 보이게 됩니다.

이미 계획 → 생성 → 평가 루프를 돌리고 있다면, 지렛대는 **계획** 단계에 있다는 뜻입니다. 평가 단계는 명시한 기준만 잡아냅니다. 모델이 짐작으로 채울 부분을 없애는 것은 계획뿐입니다.

## 이 주장이 틀리는 경우

품어 둘 반대 가설이 있습니다. **연구소들이 쓸 만한 유지보수성 판정기를 만들어 내면, 이 인과 설명은 빠르게 힘을 잃습니다.** mutation testing과 judge 모델을 묶는 시도가 정확히 그 방향입니다. 충분히 빠른 아키텍처 판정 기준을 학습에 쓸 수 있게 되면 천장은 저절로 올라가고, 앞단의 계획은 구조적으로 꼭 필요한 일에서 평범한 좋은 습관으로 내려옵니다. 또 Faros의 수치만으로는 "AI가 짰다"와 "빨리 배포하는 팀은 원래 리뷰를 건너뛴다"를 구분할 수 없습니다.
