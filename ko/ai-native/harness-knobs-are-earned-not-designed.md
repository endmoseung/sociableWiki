# harness 설정값은 미리 설계하지 않고, 실제로 겪은 실패로 얻어낸다

잘하는 엔지니어들은 agent harness의 설정값을 어떻게 *조율*하는지 궁금했습니다. effort 단계, fan-out 폭, 재시도 횟수, 턴 제한, 작업 유형별 프로필 같은 것들입니다. 논문과 벤더 문서, 실무자 글을 폭넓게 훑어보고 내린 솔직한 결론은, 대부분 조율하지 않는다는 것입니다. 구체적인 실패를 겪고 나서야 설정값을 **얻어내고**, 그 실패가 더 이상 일어나지 않으면 **지웁니다**.

## 모두의 자신감에 한계를 긋는 두 가지 측정

두 측정을 함께 읽으면 논지가 전부 드러납니다.

- **harness는 영향이 큽니다.** SWE-bench Verified 일부 문항에서 harness가 만든 편차가 모델이 만든 편차의 약 **7.8배**였습니다(18.48과 2.37 pp²).
- **그런데 무작정 고친다고 나아지지 않습니다.** 한 오픈소스 코딩 CLI의 **연속 릴리스 35개**를 모델을 고정한 채 돌린 결과(총 3,500회), 해결률에는 **유의미한 추세가 없었습니다.** 23%와 39% 사이를 오갔고 초기 릴리스가 나중 릴리스를 이기기도 했습니다. 그동안 **토큰 사용량은 약 70% 늘었습니다.**

harness를 전문으로 만드는 사람들이 쉬지 않고 고쳤는데도 개선을 증명하지 못했고, 비용은 두 배 가까이 늘었습니다. harness는 영향력이 크기 때문에 eval 없이 이리저리 바꾸면 비쌉니다. 설정 변경은 eval을 통과할 때만 하고, 그렇지 않으면 하지 않습니다.

## 이 설정값이 애초에 있어야 하는가

여러 출처가 독립적으로 "아플 때까지 하드코딩하라"보다 더 엄격한 규칙에 모입니다. 규칙이나 설정은 **구체적인 과거 실패나 피할 수 없는 외부 제약**에서 나와야 하고, 그렇지 않으면 잡음입니다. 저는 Addy Osmani의 표현을 기억해 둡니다. "Ratchet; don't brainstorm." 즉 실패가 생길 때마다 한 칸씩 조이되, 상상으로 미리 늘어놓지 말라는 뜻입니다. Hamel Husain도 eval을 두고 같은 말을 합니다. 상상한 오류가 아니라 실제로 발견한 오류에 대해 평가기를 쓰라는 것입니다. Anthropic의 agent 가이드도 결과가 확실히 좋아질 때만 복잡도를 더하라고 말합니다.

*좋은* 설정값을 가리는 가장 좋은 시험은 Amp에서 나왔습니다. Amp는 모델 선택 메뉴를 없애고 채택 수치를 공개했습니다. "smart" 모드가 새 스레드의 55%를 맡다가 일주일 만에 0이 됐고, 사용자의 69%는 새 다이얼을 기본값에서 한 번도 옮기지 않았으며, 그 밑에서 모델 공급사가 바뀌었는데도 불만이 한 건도 없었습니다. 이들의 관점 전환은 다른 곳에도 그대로 통합니다. 모델 선택 메뉴는 이 작업에 어떤 모델이 최선인지를 사용자에게 묻습니다. 난이도 다이얼은 사용자만 아는 것, 곧 *이 작업이 얼마나 어려운지*를 묻습니다.

**제대로 된 설정값은 사용자만 아는 것을 묻습니다.** 시스템이 추론할 수 있는 것이라면 그 설정값은 태어나자마자 죽은 셈입니다. 반대로 선택 메뉴를 남긴 Augment는 그게 맞는 조건을 밝혔습니다. 선택지끼리 **어느 한쪽이 늘 이기지 않을 때**, 예를 들어 품질은 둘 다 좋은데 지연 시간과 품질의 균형점이 서로 다른 두 모델일 때만 노출합니다. 한쪽이 늘 이긴다면 그쪽을 하드코딩합니다.

## 조율할 값으로 두지 말고 막아야 할 것

아예 조율 대상이 되면 안 되는 것도 있습니다.

- **다이얼이 아니라 위험 축으로 나눕니다.** OpenAI의 agent 가이드는 도구마다 읽기 전용인지 쓰기인지, 되돌릴 수 있는지, 필요한 권한, 금전적 영향을 매깁니다. 위험이 높은 행동은 사람에게 넘기고, 그 관문은 신뢰성 근거가 쌓일수록 조금씩 풀도록 설계합니다.
- **위험한 조합은 구조로 피합니다.** Simon Willison이 말한 "lethal trifecta"(비공개 데이터, 신뢰할 수 없는 입력, 외부로 나가는 통로)는 95% 안전하게 조율할 대상이 아니라 조합 자체를 만들지 말아야 할 대상입니다.
- **가짜 관문은 관문이 없는 것보다 나쁩니다.** Amp는 무시 파일 기능을 거절했습니다. 파일을 못 보게 막아도 모델은 셸 도구로 돌아가서 읽고, 결국 안전하다는 착각만 남기 때문입니다.
- **사람의 검토는 앞단으로 옮깁니다.** HumanLayer의 지적대로 잘못된 코드 한 줄은 한 줄로 끝나지만, 계획의 잘못된 한 줄은 수백 줄의 잘못된 코드가 됩니다. 사람의 검토는 수정 결과보다 조사와 계획에서 더 큰 값을 냅니다.

## 꼭 숫자를 정해야 한다면

제가 찾은 유일하게 문서화된 방법은 값이 아니라 측정 절차였습니다. **대표 표본을 제한 없이 돌려 작업별 분포를 기록하고, p99에서 시작해 조율합니다.**

크기보다 가시성이 중요합니다. 한 브라우징 벤치마크에서 ReAct 기준 모델은 context가 남아 있는데도 예산 한도에서 멈춰 더 쓰지 못했습니다. 모델에게 *보이는* 카운트다운을 주자 검색 호출이 약 40%, 비용이 약 31% 줄었고 정확도는 비슷했습니다. 다만 다른 연구는 모델이 제시된 예산을 넘기곤 하고, 한 번 준 예산은 주기적으로 다시 알려 주지 않으면 효과가 흐려진다는 것을 보여 줍니다. 그래서 할당 품질을 위해서는 보이는 예산을, 보장을 위해서는 hard cap을 둡니다. 둘 다 필요합니다.

## 근거가 만들지 말라고 하는 설정값

| 만들고 싶어지는 설정값 | 그걸 무너뜨리는 근거 |
|---|---|
| 작업별 라우터·난이도 분류기 | 한 팀이 만들었다가 폐기했습니다. 프롬프트만 보고는 난이도를 알 수 없고(context는 도구 호출을 거치며 드러납니다), 프로필을 바꿀 때마다 prompt cache가 깨집니다. |
| 작업 유형별 산문 프로필 | Vercel의 eval에서 해당 skill은 대부분의 실행에서 호출조차 되지 않았고 기준선보다 나을 게 없었습니다. 정적인 지침 파일이 더 나았습니다. |
| 프로필마다 규칙을 잔뜩 | 지시 따르기 벤치마크들은 제약이 몇 개만 넘어가도 성능이 급격히 떨어지고, 앞쪽 지시가 이기는 편향이 있으며, 턴이 길어질수록 효과가 흐려진다는 것을 보여 줍니다. |
| 기본으로 "작업을 다시 확인하라" | 최신 모델에서는 과잉 검증을 부릅니다. 부정행위를 막는 쪽에서는 환경을 단단하게 만들었더니 reward hacking이 상대적으로 87.7% 줄었고 작업 성공률은 그대로였습니다. 규칙을 더하지 말고 환경을 단단하게 만듭니다. |
| 아무도 읽지 않는 설정 키 | 호출하는 곳이 없는 로더는, 값을 바꾸면 동작이 바뀔 거라 기대하는 사람을 속입니다. harness는 자기가 중간에서 다루는 것만 강제할 수 있습니다. |
| 품질 다이얼로서의 effort 증가 | LangChain은 모델을 고정한 채 측정했는데, 가장 높은 effort 단계가 바로 아래 단계보다 오히려 점수가 낮았습니다. 원인은 시간 초과였습니다. |

독립적인 설계들이 모이는 최소 구성은 작습니다. reasoning effort 사다리 하나, 순서가 있는 자율성 단계 몇 개, 작고 고정된 도구 표면입니다. Databricks가 자사의 큰 코드베이스로 비교한 결과, 도구 4개에 MCP도 subagent도 plan mode도 없는 harness가 통과율이 가장 높았고 비용은 약 절반이었습니다. 턴마다 보내는 context가 대략 3분의 1이었기 때문입니다. 두 축을 섞지 않는 것이 중요합니다. 문체나 장황함을 설정값으로 만드는 쪽에서 썩음이 생기고, **능력**(도구 표면)을 늘리는 쪽에서 이득이 생깁니다.

## 정직하게 밝혀 둘 한계

- **fan-out, 재시도, 최대 턴 기본값에는 측정된 근거가 없습니다.** fan-out 3~5, maxTurns 30, "5번 시도하면 멈춘다", context 비율 기준, 줄 수 제한처럼 돌아다니는 숫자는 전부 주장일 뿐 벤치마크로 확인된 적이 없습니다.
- **"그냥 측정하면 된다"는 말처럼 쉽지 않습니다.** Anthropic도 자체 사후 분석에서 eval이 사용자가 겪은 품질 저하를 잡지 못했다고 인정했습니다. 사람이 결과물을 보고 나면 평가 기준도 바뀌고, judge 일치도 수치는 프로토콜이 다르면 서로 비교할 수 없습니다.
- 설정값을 소수로 유지하자는 결론은 여러 설계가 모이는 모습과 벤치마크 하나에서 끌어낸 제 추론입니다. 공개된 곡선이 있는 건 아닙니다.

## 절차

1. 실제로 실패가 있었는가? 없었다면 설정값을 추가하지 않습니다.
2. 사용자만 아는 것을 묻는가? 시스템이 추론할 수 있다면 빼 버립니다.
3. 선택지끼리 한쪽이 늘 이기지는 않는가? 한쪽이 늘 이긴다면 그쪽을 하드코딩합니다.
4. 되돌릴 수 없는 행동인가? 그렇다면 설정값이 아니라 사람이 확인하는 관문으로 둡니다.
5. 우회할 수 있는가? 그렇다면 구조로 막거나 아예 두지 않습니다.
6. 숫자는 측정해서 정합니다. 제한 없이 실행하고, 분포를 보고, p99에서 시작해 조율합니다.
7. 지울 계획도 세워 둡니다. 모델 업그레이드는 모든 설정값을 다시 감사하기 좋은 시점입니다.

feature flag 운영에서 빌려 올 만한 관리 지표도 있습니다. 설정값 개수가 아니라 **flag 반감기**(만든 뒤 지울 때까지 걸린 시간의 중앙값)를 추적합니다. 오래된 설정은 알려진 장애 원인입니다. 한 클라우드 장애 연구는 생성형 AI 서비스 장애의 약 4분의 1을 설정 문제로 분류했고, 그중 일부는 한 구성 요소의 설정 변경이 다른 구성 요소를 깨뜨린 경우였습니다.

**이 원칙이 틀리는 경우:** 비용 상한, 규정 준수, 되돌릴 수 없는 행동 같은 외부 제약은 실패를 겪기 전에 설계 단계에서 관문을 둡니다. "실패로 얻어낸다"는 조율용 설정값에 대한 이야기이고, 안전의 바닥선에는 적용하지 않습니다.
