# 모델 업그레이드는 지울 것을 찾는 시점이다

모델이 강해지면 harness 지침의 적정량은 **늘지 않고 줄어듭니다.** Anthropic은 2026년 7월 Claude 5 계열에 맞춰 Claude Code를 다시 조율한 글에서, **Claude Code 자체 system prompt의 80% 넘게 지웠는데 코딩 eval에서 측정 가능한 손실이 없었다**고 밝혔습니다. 커뮤니티 사례도 비슷한 범위에 들어옵니다. 어떤 `CLAUDE.md`는 260줄에서 165줄로(약 37%), 어떤 18개짜리 agent 묶음은 8,798줄에서 664줄로(약 92.5%) 줄었고, 그중 가장 큰 agent 하나는 951줄에서 91줄이 됐습니다.

여기서 얻을 교훈은 "글을 짧게 써라"가 아닙니다. **업그레이드가 남길 것과 지울 것의 경계를 옮긴다**는 점입니다. 이전 모델에서는 꼭 필요했던 지침이 새 모델에서는 죽은 비계가 되고, 죽은 비계는 무해하지 않습니다. 더 강한 모델의 동작을 실제로 망칩니다(과잉 검증, 과잉 신중함). 그래서 새 모델이 나오면 무엇을 더할지 다시 쓰기보다 **무엇을 지울지 다시 감사**해야 합니다.

## 모든 줄에 던지는 질문 하나

규칙 전체가 질문 하나로 줄어듭니다.

> 이 줄이 없으면 강한 모델이 *더 나쁘게* 동작하는가? 아니라면 지웁니다.

정직하게 적용하면 보통의 지침 파일에서 절반 정도가 빠집니다. 이렇게 많이 빠지는 이유는, 대부분의 지침이 *더 약한* 모델의 실패를 메우려고 쓰였고 그 땜질이 실패보다 오래 살아남기 때문입니다. 다음 네 부류는 거의 항상 이 질문을 통과하지 못합니다.

1. **역할 연기** — "당신은 시니어 엔지니어입니다…" 같은 문장입니다. 토큰만 들고, 유능한 모델의 동작은 하나도 바꾸지 못합니다.
2. **일반 지식 반복** — 모델이 사전 학습으로 이미 아는 내용입니다.
3. **강조용 비계** — `IMPORTANT`, 전부 대문자, 이모지, 무게를 실으려는 반복입니다. 강한 모델에게는 주의를 비트는 잡음일 뿐 지렛대가 되지 못합니다.
4. **중복된 검증 요구** — "작업을 다시 확인하라" 같은 문장입니다. Claude Opus 5에서는 이 문장이 과잉 검증을 일으켜 품질은 그대로인데 토큰만 태운다는 것이 확인됐고, 지웠더니 오히려 이득이었습니다.

이 질문을 *통과하는* 것은 적고 구체적입니다.

- 모델이 추론할 수 없는 **운영자의 의견**(자동화할지 손으로 할지, 팀의 문체 선택)
- **의외의 프로젝트 사실**(생성된 파일, 배포일에 조심할 점, 눈에 띄지 않는 환경 설정)
- **실제 숫자 기준이 있는 라우팅 규칙**
- **이름이 정해진 연동 대상**(특정 서비스, 엔드포인트, 환경 변수 이름)

이 모양 자체가 요점입니다. 살아남는 것은 정확히 모델이 *스스로 알아낼 수 없는* 것, 곧 내 선호와 내 로컬 사실입니다. 이것이 어떤 모델 릴리스도 흡수하지 못하는 harness의 오래가는 층입니다. 모델이 스스로 알아낼 수 있는 내용은 언젠가 지워질 운명입니다.

## 분량을 줄이는 일이 아니라, 규칙을 어디에 둘지 정하는 일

규칙마다 맞는 자리가 있습니다. 항상 켜져 있는 지침 파일, 필요할 때 불러오는 skill, hook, subagent, 권한 설정 중 하나입니다. 모델 업그레이드는 그중 **항상 켜져 있는** 층에 얼마나 남길지를 더 날카롭게 정해 줍니다. 이 층이 가장 비싼 자리이기 때문입니다. 매 턴 비용을 내고, 강조용 비계가 주의를 가장 크게 망가뜨리는 곳도 여기입니다. Anthropic은 삭제의 배경으로 여섯 가지 변화를 꼽았고, 하나하나가 사실상 "이건 항상 켜진 층에서 비용을 그만 내자"는 결정입니다.

| 변화 | 이전 | 이후 | 항상 켜진 prompt에 생기는 효과 |
|---|---|---|---|
| 규칙에서 판단으로 | 단계별 지시 | 기준만 주고 결정은 모델에게 | 일일이 적을 분기가 줄어듭니다 |
| 예시에서 인터페이스로 | 산문 속 few-shot 예시 | 의도가 드러나는 도구·파일 구조 설계 | 예시가 tool schema로 옮겨 갑니다 |
| 미리 다 싣기에서 점진적 공개로 | 모든 내용을 지금 context에 | 가끔 쓰는 내용은 skill이나 규칙 파일 뒤에 | 라우팅 안내만 남습니다 |
| 반복에서 한 번 설명으로 | 같은 규칙을 여러 층에 | 한 번만 적음 | 층 사이 중복이 사라집니다 |
| 손으로 관리하는 메모리에서 자동 메모리로 | 사람이 고치는 문서 | 시스템이 관리하는 context | 수동 메모리가 줄어듭니다 |
| 얇은 명세에서 풍부한 참고 자료로 | 산문 명세 | 테스트, 코드, 목업이 결과물 | 의도를 정밀한 결과물이 전달합니다 |

내용이 꼭 사라지는 건 아닙니다. **더 싸고 필요할 때만 불러오는 자리**(skill, 규칙 파일, 테스트)로 옮겨 가거나, 이제 모델이 알아서 하니 빠질 뿐입니다. context 예산 가운데 고정으로 늘 실리는 부분부터 줄입니다.

## 이 원칙이 막아 주는 함정 두 가지

- **더하기만 하는 습관.** 결과가 나쁘면 반사적으로 "더 신중하게", "항상 검증하라" 같은 줄을 *더합니다.* 강한 모델에서는 반대가 답인 경우가 많습니다. 이미 있는 과잉 지시가 나쁜 결과를 *만들고* 있을 수 있습니다. 더하기 전에, 이미 있는 줄에 삭제 질문부터 던집니다.
- **옮긴다고 지운 것은 아니고, 옮긴 규칙은 조용히 죽을 수 있습니다.** 가끔 쓰는 규칙을 항상 켜진 파일에서 skill로 옮기는 건 매 턴 내던 비용을 멈추니 맞는 선택입니다. 다만 옮긴 규칙은 계속 *닿을 수 있어야* 합니다. 아무도 부르지 않는 skill은 죽은 비계를 죽은 기능으로 바꿔 놓았을 뿐입니다.

## 운영 규칙

새 최신 모델이 나올 때마다 다음을 합니다.

1. 항상 켜진 지침 파일, agent 정의, skill 본문에 "이 줄이 없으면 강한 모델이 더 나빠지는가?"를 한 번씩 던집니다.
2. 역할 연기, 일반 지식 반복, 강조용 비계, 중복 검증 요구를 지웁니다.
3. 가끔 쓰는 내용은 skill이나 규칙 파일로 옮기고, 여전히 불러와지는지 확인합니다.
4. 운영자 의견, 의외의 로컬 사실, 숫자 기준이 있는 라우팅 규칙, 이름이 정해진 연동 대상은 남깁니다.

성숙한 지침 파일이라면 절반 정도, 지나치게 자세히 적힌 agent 묶음이라면 그보다 훨씬 많이 지우게 될 거라고 예상합니다.

**이 원칙이 틀리는 경우:** 더 작은 모델로 내리거나 일부 요청을 작은 모델로 보낸다면, 지운 비계가 그쪽에서는 아직 필요할 수 있습니다. 삭제 질문은 모델마다 따로 던져야 하고, 모든 모델에 한 번에 통하지 않습니다. 또 보고된 수치는 코딩 eval에서 나왔습니다. 벤더가 평가하지 않은 영역에서는 코딩 eval이 필요 없다고 한 줄이 여전히 필요할 수 있습니다. 삭제를 믿기 전에 자기 작업으로 다시 확인합니다.
