# 누가 풀고 누가 검증하나: 검증자에게서 생성 맥락을 빼야 합니다

코딩 에이전트를 여러 개 돌리다 보면 같은 배치 문제를 계속 만납니다.

- **A안**: subagent 여러 개가 각자 풀고, 메인 에이전트가 그중 하나를 골라 검증합니다.
- **B안**: 메인 에이전트가 하나를 풀고, subagent들이 그 결과를 검증합니다.

논문들은 B안 쪽을 가리킵니다. 그런데 정말 중요한 변수는 "메인이냐 subagent냐"가 아닙니다. **판정하는 쪽이 그 답을 자기 생각으로 쥐고 있느냐**입니다. 답을 직접 만들었거나, 답을 만든 추론을 물려받은 판정자는 어느 프로세스에서 돌든 약한 판정자입니다. 저도 예상하지 못했던 부분은, B안도 순진하게 하면 진다는 점이었습니다.

## 자기 리뷰가 구조적으로 약한 이유

한 연구는 틀린 추론을 바이트 하나 바꾸지 않고 위치만 옮겨 봤습니다. 모델 자신의 thought 블록 안에 두는 경우와, memory 블록이나 user 메시지 안에 두는 경우를 비교한 겁니다. 같은 글을 외부 내용으로 보여 주자 오류를 명시적으로 짚어 내는 비율이 대략 23~93%p 올랐습니다(arXiv:2606.05976). 저자들은 이 현상을 *addressability*라고 부릅니다. 자기 생각 흐름 속의 오류에는 가리킬 대상이 없고, 외부 라벨이 붙은 내용에는 있다는 뜻입니다. 오류를 알아차리는 능력은 멀쩡한데, 그걸 붙잡고 행동할 손잡이가 없는 셈입니다.

예전 자기 교정 연구들도 같은 방향을 가리킵니다.

- GPT-4가 GSM8K에서 스스로 답을 고치게 하자 정답률이 95.5%에서 89.0%로 떨어졌습니다. 오답을 정답으로 고친 경우보다 정답을 오답으로 바꾼 경우가 조금 더 많았습니다. 외부에서 정답 여부를 알려 주자 부호가 뒤집혔습니다(Huang et al., arXiv:2310.01798).
- 코드 수리에서는 고치는 단계가 아니라 *찾는* 단계가 병목이었습니다. 같은 수리 모델과 같은 코드에서 모델의 자기 피드백을 사람 피드백으로 바꾸자 통과한 프로그램이 약 57% 늘었습니다(Olausson et al., arXiv:2306.09896).
- Self-Correction Bench에서는 모델이 낸 오류 대부분이 자기 검사를 통과했고, 같은 내용을 외부 것으로 보여 주면 잡혔습니다.

그래서 A안에는 숨은 약점이 있습니다. 메인이 어느 subagent의 결과를 채택할지 정하는 순간, 메인은 이미 리뷰어입니다. 메인의 선호가 그 선택에 그대로 섞여 들어갑니다.

## A안의 천장은 fan-out이 아니라 판정자가 정합니다

생성은 늘릴수록 커지지만 선택은 그렇지 않습니다. 반복 샘플링에서 샘플 중 하나라도 정답인 비율은 10,000개에서 95.3%까지 올랐습니다. 반면 다수결과 best-of-N으로 골라낸 정답률은 약 100개 이후 40% 근처에서 멈췄습니다(Brown et al., arXiv:2407.21787). solver를 몇 개 이상 늘리면 판정자가 고르지 못하는 더미만 커집니다.

게다가 판정자가 solver와 닮을수록 이득이 줄어듭니다. 37개 모델과 9개 벤치마크에서 다른 계열 모델의 검증이 같은 계열보다 나았고, 같은 계열이 자기 검증보다 나았습니다. 자기 검증의 오탐은 모델이 커질수록 오히려 늘었습니다(arXiv:2512.02304). "메인이 더 강하니 판정을 맡기면 된다"는 생각은 성립하지 않습니다.

## 리뷰어 띄우는 방식을 바꾼 결과

한 연구는 Claude Opus 4.6을 Claude Code의 Agent 도구로 돌려, 오류 150개를 심은 산출물 30개를 총 360번 리뷰하게 했습니다(arXiv:2603.12123).

| 리뷰 조건 | F1 |
|---|---|
| 새 세션, 산출물만 전달 | **28.6%** |
| 같은 세션에서 자기 리뷰 | 24.6% |
| **생성 프롬프트를 물려받은 subagent** | **23.8%** |
| 같은 세션에서 두 번 리뷰 | 21.7% |

산출물이 어떻게 만들어졌는지 아는 subagent가 그냥 자기 리뷰보다도 *낮았습니다*. 효과를 낸 건 리뷰어를 띄운 행위가 아니라 **맥락이 없다는 사실**이었습니다. 비용도 더 쌉니다. 새 리뷰 세션은 쌓인 대화 기록을 다시 읽지 않으니 약 5K 토큰을 썼고, 생성 세션은 약 50K를 썼습니다.

저자들도 인정한 한계가 하나 있습니다. 자기 리뷰는 한국어로, 새 세션 리뷰는 영어로 돌려서 28.6과 24.6의 차이 일부는 언어 효과일 수 있습니다. 다만 23.8과 28.6은 둘 다 영어라 이 교란이 없고, addressability 연구도 같은 방향을 따로 뒷받침합니다.

그래서 제가 얻은 설계 규칙은 "subagent를 띄워라"가 아닙니다. **"검증자에게 생성 맥락을 주지 마라"**입니다.

## 검증자에게 추론 과정을 보여 줘야 할까

판정자에 따라 정반대로 갈리고, 그 효과는 정보가 아니라 설득입니다. Natural Questions에서 추론까지 보여 주자 작은 판정자(Qwen3-8B)는 정확도가 58.2%에서 33.2%로 떨어졌고, GPT-4o는 그대로였고, Claude Sonnet 4.5는 75.8%에서 84.0%로 올랐습니다(arXiv:2604.06756). 상관없는 추론이나 사실과 반대인 추론도 판정을 크게 움직였습니다. 추론을 답 앞에 두면 뒤에 둘 때보다 훨씬 해로웠는데, 이는 앵커링의 전형적인 흔적입니다. 다른 연구에서는 출처 라벨만 "전문가"로 바꿔도 판정이 약 18% 움직였습니다. 판정자는 그 라벨을 한 번도 언급하지 않고 내용 품질을 근거로 들었습니다(arXiv:2509.26072).

진짜 축은 **무엇을 먼저 확정하느냐**입니다. 검증자가 추론을 읽기 *전에* 자기 기대를 먼저 적게 하자 실패 탐지가 약 25%p 올랐습니다(arXiv:2507.11662). 추론을 넘긴다면 이 단계 뒤에, 판정 근거가 아니라 조사할 단서로 넘깁니다.

## 검증이 오히려 손해가 되는 경우

- **같은 모델끼리의 debate.** 작은 모델에 debate를 붙이자 그 모델의 zero-shot보다 점수가 낮았습니다. 통제 실험에서는 상관없는 노이즈가 진짜 비평을 이겼습니다(arXiv:2605.00914). 효과를 낸 건 비평이 아니라 흔들기였습니다.
- **solver에게 돌아가지 않는 비평.** 한 수학 연구에서 정밀도 0.861인 리뷰어가 0.644인 리뷰어에게 졌습니다. 정밀도가 낮은 쪽 비평은 93.5%가 반영됐고 높은 쪽은 33.6%만 반영돼, 최종 통과율은 낮은 쪽이 더 높았습니다(arXiv:2607.15388). 결정적인 건 비평이 solver의 맥락으로 돌아가 다음 결과를 바꾸느냐입니다. 권위 있는 판정이 아니라 동료의 의견처럼 전달하자 반영률이 세 배가 됐습니다.
- **쉬운 작업.** 한 번에 성공하는 비율이 이미 0.9를 넘으면, 제가 읽은 자료들은 이득이 거의 0이고 토큰만 몇 배로 든다는 데 의견이 같았습니다.

## A안이 이기는 경우

읽기 전용이고, 쪼갤 수 있고, 에이전트끼리 의존이 없고, **맥락의 양이 병목**인 작업입니다. 리서치가 대표적입니다. Anthropic이 멀티 에이전트 리서치 시스템을 소개한 글에서는 이 영역에서 90.2% 개선을 보고하면서, 대부분의 코딩 작업은 그만큼 병렬화되지 않는다고 분명히 적었습니다. 통제된 연구에서는 사고 토큰 예산을 고정하면, 가장 작은 예산을 빼고는 단일 에이전트가 멀티 에이전트 구조 6종을 이기거나 비겼습니다. 그런데 단일 에이전트 맥락의 70%를 가리자 결과가 뒤집혔습니다(Tran & Kiela, arXiv:2604.02460). 멀티 에이전트가 이기는 건 맥락이 망가질 때 생기는 현상입니다. 에이전트 하나가 맥락을 제대로 쓸 수 있다면 구조를 더 얹을수록 손해입니다.

## 제가 쓰는 규칙

1. **작성은 메인 스레드 하나에서 합니다.** 여러 에이전트가 동시에 읽는 건 안전하지만, 동시에 쓰면 서로 어긋나는 암묵적 선택이 생깁니다.
2. **검증은 subagent에게 산출물만 주고 맡깁니다.** 메인의 추론 과정, 스펙이나 계획, 자기 평가나 자신감 표현은 넘기지 않습니다.
3. **검증자는 추론을 보기 전에 자기 기대를 먼저 적습니다.**
4. **발견한 문제는 메인 맥락으로 돌려보내고 메인이 고칩니다.**
5. **재시도는 두 번까지입니다.** 그 이상은 포화되거나 같은 자리를 오갑니다.

검증 층을 붙이기 전에 두 가지를 먼저 봅니다. 한 번에 성공하는 비율이 이미 0.9 정도를 넘으면 붙이지 않습니다. 푸는 비용이 검증 비용의 2.5배를 넘지 않으면 검증 대신 시도를 더 합니다. 이 비율은 내 작업 20~30개를 샘플로 잡아 직접 잽니다. 이 수치는 검색 작업에서 나온 것이고, 코딩에서는 아직 측정된 적이 없습니다.

## 이 규칙이 틀리는 경우

- **기계로 정답을 확인할 수 없는 작업.** 기획, 설계, 글쓰기처럼 정답 판정을 자동화할 수 없으면 LLM 판정자는 객관식 작업보다 사람과 훨씬 덜 일치합니다. 이때 B안은 비싼 노이즈가 됩니다. 저는 이런 작업에서 검증을 사실과 일관성 같은 최소 기준을 지키는 데만 쓰고, 품질을 끌어올리는 용도로는 쓰지 않습니다.
- **질문에 딱 맞는 실험이 없습니다.** 같은 토큰 예산에서 solver 1개와 verifier N개, solver N개와 verifier 1개를 직접 비교한 논문은 찾지 못했습니다. 위 결론은 여러 연구를 엮은 추정이지 직접 측정한 결과가 아닙니다.
- **과도기 기술일 수 있습니다.** 생성 모델이 좋아질수록 리뷰어 능력과 상관없이 비평의 가치가 떨어진다는 결과도 있습니다.
