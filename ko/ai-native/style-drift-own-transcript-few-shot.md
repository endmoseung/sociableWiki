# 문체 규칙은 에이전트 자신의 대화 기록에 집니다

## 한 줄 요약

세션 시작 지점(system prompt, output style, CLAUDE.md)에 둔 문체 규칙은 처음 몇 턴은 잘 지켜지다가 점점 흐려집니다. "규칙이 멀리 있어서"는 이유의 일부일 뿐입니다. 20~30턴쯤 되면 context에는 모델이 **직접 쓴 답**이 수십 개 쌓이고, 이 답들이 가장 가깝고 가장 많은 문체 예시가 됩니다. 모델은 이 답들을 암묵적인 few-shot 예시로 삼아 계속 따라 합니다.

그래서 답 하나가 어긋나면(요약 문단, 표어 같은 문장, em dash) 그 어긋남이 다음 답의 예시가 됩니다. 문체가 흐트러지는 현상은 **스스로를 키웁니다**. 일반적인 작업 지시가 희미해지는 것과는 다릅니다. 에이전트를 에러 루프에 가두는 자기 조건화와 같은 원리가 정확성 대신 형식에 작용하는 셈입니다. 다만 해법은 다릅니다. 히스토리를 줄이는 대신, 창은 그대로 두고 규칙을 끝으로 옮깁니다.

실무에서 따라오는 결론은 두 가지입니다.

1. **규칙을 줄인 사본을 매 턴 끝에 다시 넣습니다**(`UserPromptSubmit` hook). **subagent에게도 따로 사본을 건넵니다**(`SubagentStart` hook). subagent는 자기 system prompt로 시작하기 때문에 본 세션의 output style을 물려받지 않습니다.
2. **판단이 필요한 범주보다 글자로 검사하는 금지어를 씁니다.** "em dash 금지", "1인칭 금지"처럼 문자열로 확인할 수 있는 금지어는 어디에 둬도 지켜집니다. "은유 금지", "표어 금지" 같은 모호한 범주는 문구와 위치가 맞아야 겨우 움직이거나, 아예 움직이지 않습니다.

## 근거: 실무자 벤치마크 하나

2026년 10월 Hacker News에 소개된 Claude Code plugin `terse`의 작성자가 벤치마크를 공개했습니다. 규칙 문구와 배치 8가지를 20~40개 프롬프트에 대해 `claude -p`로 한 번씩 돌렸고, 당시 모델인 Opus 5.5와 Fable 5.1을 썼으며, 정규식 계수기와 LLM 판정자로 채점했습니다.

| 관찰 | 수치(한 번 실행, 작성자 측정) |
|---|---|
| 채팅 답 중앙값, 규칙 없음 대비 규칙 있음 | 636 → 181단어 |
| 프롬프트 12개 기준 출력 토큰 | −45% |
| 채팅 답 120개와 문서 57개의 em dash 수, **모든** 구성에서 | 0 |
| 판정 범주(관점 바꾸기, 리듬)의 배치·문구별 변화 | 15~60% 변동 |
| 판정 범주 "은유"의 변화 | 어떤 구성에서도 움직이지 않음 |
| 턴마다 붙이는 끝 알림의 비용 | 입력 토큰 약 145개 |

비교 기준은 같은 규칙을 CLAUDE.md에만 두고 다시 넣지 않은 구성이었고, plugin의 output style과 끝 알림을 함께 쓰면 답 길이가 대략 절반으로 줄었습니다. 저는 이 수치를 방향만 보여 주는 값으로 봅니다. 프롬프트당 한 번만 돌렸고, 판정은 LLM이 했고, plugin 작성자가 자기 plugin을 채점했기 때문입니다.

## 작동 원리

```
1턴:   [system: 문체 규칙] [user] → 규칙을 따른 답
25턴:  [system: 문체 규칙] ... [자기 답 24개, 일부는 어긋남] [user]
                                ^^^^^^^^^^^^^^^^^^^^^^^^^^^^
                                가장 가까운 예시 → 따라 함
해법:  ... [자기 답 24개] [user + <줄인 규칙>]   ← 끝에 다시 넣기
```

- context 앞쪽의 규칙은 context 안 예시들의 **최근성**과 **양**을 상대로 싸웁니다. 두 가지 모두 대화 기록이 이깁니다.
- 끝 알림이 효과를 내는 이유는 진행 상황 파일을 다시 읽게 하는 방법이 통하는 이유와 같습니다. 위치를 이용하는 장치이지, 오래 지속시키는 장치가 아닙니다. 이미 어긋난 과거 답은 고치지 못합니다. 그건 세션을 비우거나 compaction해야 정리됩니다.
- subagent는 따로 샙니다. 벤치마크에서 subagent의 문체는 본 세션 규칙보다 **subagent가 쓰는 모델**을 주로 따랐고, `SubagentStart`에서 규칙을 건넨 뒤에야 맞춰졌습니다.

## 제가 적용하는 방법

- 규칙이 **형식**(길이, 어조, 문장부호)에 관한 것이라면 긴 세션에서 한 번 배치한 것만 믿지 않습니다. 짧은 끝 알림을 붙이고, 매 턴 비용이 드니 작게 유지합니다. 끝에 붙기 때문에 캐시된 앞부분은 건드리지 않습니다.
- 규칙은 지켜야 할 형식과 금지어를 함께 적습니다. "마지막 문장은 사실을 말합니다. 마무리 제안은 쓰지 않습니다." 금지어는 검사할 수 있고 잘 붙어 있습니다. 범주는 판정자가 필요하고 그래도 샙니다.
- 읽어 보는 대신 셉니다. 바꾸기 전과 후의 답 N개에 정규식을 돌려 금지 문자열 개수를 비교합니다.
- subagent의 출력이 사람에게 간다면 규칙을 subagent에도 명시적으로 넘깁니다.

## 이 패턴이 틀리는 경우

- **짧은 세션**(대략 10턴 미만). 앞에 둔 규칙이 대화 기록에 질 일이 없으니 끝 알림은 순수한 부담입니다.
- **길이가 실제로 일을 할 때.** 답이 짧아지면 검토자에게 필요한 근거와 불확실성이 빠질 수 있습니다. 서술은 줄이되 근거는 줄이지 않습니다. 빡빡한 단어 수 제한은 숙련된 독자에게 맞춘 선택이지, 모든 독자에게 쓸 기본값이 아닙니다.
- **thinking 토큰이 비용 대부분을 차지할 때.** 답 길이 규칙은 비용보다 눈에 보이는 단어를 더 많이 줄입니다. 벤치마크에서 Opus의 답은 단어가 54% 줄었지만 비용은 32%만 줄었습니다.
