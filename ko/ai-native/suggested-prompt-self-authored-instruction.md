# 추천 다음 프롬프트는 에이전트가 직접 쓴 지시입니다

## 기능 소개

Claude Code는 한 턴이 끝나면 입력창에 다음에 보낼 만한 메시지를 회색 글씨로 미리 채워 둡니다. "테스트 돌려 줘", "커밋해 줘", "잘 되는지 확인해 줘" 같은 문장입니다. 키 하나로 받아들이고, 다른 글자를 치면 사라집니다. 설정에서 끌 수도 있습니다.

2026년 10월에 이 기능이 사실은 학습용 라벨을 싸게 모으는 통로라고 주장한 블로그 글이 크게 화제가 됐습니다. 받아들이면 긍정 라벨, 고치면 선호 비교 데이터가 된다는 주장이었습니다. 이에 대해 Claude Code 팀의 엔지니어는 그렇지 않다고 답했습니다. 추천은 사용자가 흐름을 이어 가거나 다시 돌아온 사용자가 다음 할 일을 떠올리도록 돕기 위한 것이고, 추적하는 건 수락률뿐이라는 설명이었습니다. 저는 데이터 수집 해석은 반박된 것으로 봅니다. 어차피 쓸모 있는 교훈은 사용자 쪽에 있습니다.

## 받아들이면 실제로 일어나는 일

추천 문장은 **세션을 바라보는 모델 자신의 관점에서, 사용자가 다음에 내릴 지시를 예측한 것**입니다. 이걸 받아들이면 다음 지시를 쓴 쪽과 실행할 쪽이 같은 에이전트가 됩니다.

추론 과정은 이렇습니다.

1. 대화형 루프에서 바깥 관점이 들어오는 지점은 사람의 턴 하나뿐입니다. 범위, 우선순위, "그런 뜻이 아니었는데" 같은 말이 여기서 들어옵니다.
2. 추천 프롬프트는 에이전트가 작업을 이해한 방식에서 나옵니다. 받아들여도 바깥 관점은 하나도 더해지지 않습니다. 루프는 조용히 에이전트 → 에이전트로 바뀝니다.
3. 토론에 참여한 사람들도 이 끌림이 실제로 있다고 말했습니다. 추천이 생각을 끊어서 그냥 따라갈 때가 있다는 이야기가 여럿 나왔고, 그러면 추천은 예측이라기보다 스스로 실현되는 쪽에 가까워집니다.
4. 그래서 **검증 지점**(수정안 수락 여부, 범위 확인, "완료" 판단)에서 추천을 받아들이면 사람이 지키던 관문이 자기 승인으로 바뀝니다. 에이전트가 쓴 테스트로 에이전트가 쓴 코드를 채점하는 것과 같은 실패입니다.

에이전트에게 내 진단 대신 증상을 건네라는 조언과 거울처럼 맞닿아 있습니다. 그쪽은 사람의 추측이 에이전트를 붙잡아 원인 탐색을 건너뛰게 만드는 문제입니다. 이쪽은 에이전트의 추측이 사람을 붙잡아 사람의 판단을 건너뛰게 만드는 문제입니다.

## 판단 기준

| 다음 턴이… | 추천을 받아들일까? | 이유 |
|---|---|---|
| 기계적이고 이미 정해진 일(테스트 실행, 포맷, 통과 확인 뒤 커밋) | 괜찮습니다 | 넘겨주는 판단이 없습니다 |
| 검증 요청("확인해 줘", "다 된 것 같아?") | 고쳐 씁니다 | *무엇을* 검증할지, 어떤 증거(`file:line`, 명령 출력)를 원하는지 적습니다 |
| 범위나 방향(다음 기능, 다음에 잡을 버그) | 직접 씁니다 | 이 턴의 가치는 전부 내 바깥 관점에서 나옵니다 |
| 오래된 세션으로 돌아왔을 때 | 계획이 아니라 메모로 읽습니다 | 에이전트가 어디서 멈췄다고 보는지를 담고 있고, 그 내용은 낡았을 수 있습니다 |

제가 찾은 가장 싼 습관은 이겁니다. 추천이 거의 맞지만 딱 맞지는 않을 때, 그대로 받거나 무시하지 말고 **더 구체적인 지시로 고쳐 씁니다**. "테스트 돌려 줘"를 "인증 테스트만 돌려 줘. 전체는 10분 걸려"로 바꾸는 식입니다. 프로젝트에 대한 제 지식은 바로 이 고쳐 쓰기를 통해 들어갑니다.

회색 글씨가 집중을 깬다면(토론에서도 여러 사람이 그렇다고 했습니다) 꺼 버리면 됩니다. 이 기능에 기대는 다른 기능은 없습니다.

## 이 원칙이 틀리는 경우

실행을 시작하기 전에 승인된 계획에서 다음 단계가 이미 정해져 있다면 이야기가 다릅니다. 예를 들어 planner → generator → evaluator 흐름에 수락 기준이 문서로 적혀 있다면, 추천은 사람이 이미 내린 결정을 되풀이할 뿐입니다. 받아들여도 독립성을 잃지 않습니다. 위험은 다음 단계를 에이전트 말고는 누구도 정한 적 없는, 계획 없는 대화형 루프에만 해당합니다.
