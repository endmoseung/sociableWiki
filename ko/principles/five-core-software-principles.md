# 에이전트가 코드를 쓰는 시대에 다시 세운 소프트웨어 5원칙

물려받은 정전(正典)이 아니라, 프로젝트를 가리지 않고 제가 실제로 꺼내 쓰는 다섯 개의 규칙입니다.
이걸 굳이 다시 정리하는 이유는 이제 이 규칙들이 돌아가는 세계가 달라졌기 때문입니다. 코드의 주
저자는 보통 AI 에이전트이고, 저는 리뷰어입니다. 이 한 가지 변화가 아래 다섯 규칙 전부의 무게중심을
다시 잡습니다. 그래서 원칙에 들어가기 전에, 이들을 다시 빚어내는 메타 맥락 세 가지를 먼저 짚습니다.

**메타 변화, 세 가지로:**

- **셋업 비용은 분산되고, 태스크마다 드는 비용은 매번 지불된다.** 규칙 하나를 도구에 한 번 새겨두면
  비용은 한 번 내고 이득은 계속 걷습니다. 반대로 "X 하는 걸 잊지 말자" 수준으로만 남은 규칙은 매
  태스크마다 비용이 들고, 매번 잊힐 수도 있습니다. 그래서 자동화는 늘 규율(discipline)을 이깁니다 —
  저자에게 어제 태스크의 기억이 없다면 더더욱 그렇습니다.
- **코드는 처음 읽는 순간 의도를 드러내야 한다.** 사람 저자에게는 근육 기억이 있습니다. 지난주에
  `processItem`을 직접 짰으니 지금도 그게 뭘 하는지 압니다. 하지만 새 세션에서 막 시작한 에이전트는
  그게 없습니다. 이름·테스트·주석이 첫 읽기에서 *왜*를 실어 날라야 합니다. 기댈 누적 맥락이 없으니까요.
- **삭제 가능성이 확장 가능성을 이긴다.** 한 모듈의 다음 변경은 이제 조심스러운 확장보다 *재작성*일
  확률이 높습니다 — 에이전트는 파일 하나를 통째로 다시 생성하는 걸 개의치 않으니까요. 그래서 "제자리
  확장이 쉬움"보다 "삭제하고 갈아끼우기 쉬움"이 더 값집니다.

이 세 가지를 염두에 두세요. 각 규칙이 왜 그쪽으로 기우는지를 설명해줍니다.

## 1. 경계가 지저분함을 떠안는다

side effect, 검증(validation), 의존성 방향 — 이 셋은 전부 **시스템 경계(boundary)**에 삽니다. 코어는
순수하게 남습니다.

구체적인 수는 이렇습니다. 외부 입력을 경계에서 **딱 한 번** 파싱해 타입 있는 값으로 바꿉니다. 그
지점부터 안쪽으로는 타입 자체가 유효성의 증명입니다. branded 타입이나 nominal 타입을 써서 "이건 이미
파싱·검증됐다"는 사실을 타입에 실어 깊은 함수까지 그대로 흘려보내세요. 세 겹 아래에서 방어적으로 다시
검증할 일이 없어집니다.

```ts
// 경계: raw string이 신뢰 가능한 값으로 바뀌는 유일한 자리
type Email = string & { readonly __brand: "Email" };
function parseEmail(raw: string): Email { /* 한 번 검증하고 brand를 붙인다 */ }

// 코어: 시그니처가 이미 검증됐음을 보장한다
function sendReceipt(to: Email) { /* 재검증 없음, 방어적 `if` 없음 */ }
```

경계에서 `parseEmail`이 한 번 돌고 나면, 코어 안쪽 어디에서도 "근데 이게 진짜 이메일 맞아?"를 되묻지
않습니다 — 타입이 이미 답했으니까요. 지저분함(I/O, 잘못된 입력, 빠진 필드)은 가장자리에 격리되고,
가운데는 지루하고 순수합니다.

**이게 안 맞을 때:** 신뢰할 수 있는 파일 하나를 읽어 숫자 하나를 찍고 끝나는 일회성 스크립트라면
경계 계층이 필요 없습니다. 신뢰할 수 없는 가장자리 자체가 없는 코드에 파싱·branding 비용을 치르지
마세요.

## 2. 불가능한 상태는 표현 자체를 막는다

boolean 뭉치보다 **discriminated union**을 씁니다. 코어에서는 에러를 던지는 예외 대신 **값**
(`Result<T, E>`)으로 모델링하고, `try/catch`는 바깥 껍데기에만 둡니다.

플래그 뭉치 — `{ isLoading, isError, data, error }` — 는 실제로는 일어날 수 없는 상태(`isLoading`과
`isError`가 동시에 true)까지 표현할 수 있게 합니다. union은 그런 상태를 표현 불가능하게 만듭니다.

```ts
type Fetch<T> =
  | { status: "loading" }
  | { status: "success"; data: T }
  | { status: "error"; message: string };
```

이제 "에러 메시지를 든 채 로딩 중"은 애초에 만들어낼 수가 없습니다. 그래서 하위 코드 어디에서도 그
경우를 방어할 필요가 없습니다.

**이게 안 맞을 때 — 그리고 이게 중요한 경계입니다:** 이 원칙은 **안정화된** 코어에 적용하세요. 아직
*발견해 나가는 중*인 상태 기계 — 릴리스마다 단계가 바뀌는 결제(checkout) 플로우 같은 것 — 는 한두
릴리스는 느슨하게 두는 게 낫습니다. 아직 이해하지 못한 모양에 union을 잠가버리면, 배우는 내내 타입
시스템과 싸우게 될 뿐입니다. 모양이 더 이상 움직이지 않을 때 조이세요. 그 전이 아니라.

## 3. 삭제를 기준으로 최적화한다

한 모듈의 올바른 잣대는 "확장하기 쉬움"이 아니라 "**삭제하기 쉬움**"입니다. Greg Young의 1주일 규칙이
자입니다. 그 모듈에 익숙하지 않은 기여자가 처음부터 다시 짜는 데 1주일을 넘겨서는 안 됩니다. 넘긴다면
너무 얽혀 있는 겁니다.

우선순위 사다리는 이 순서입니다.

**Delete > Abstract > Duplicate > Generalize.**

중복(duplicate)이 어디 있는지 보세요. 저는 추상화 전에 **복사본 두 개**까지는 허용합니다 — rule of
three(3의 규칙)입니다. 공통 모양이 처음 보이면 우연이고, 두 번째면 예감이며, 세 번째로 나타났을 때
비로소 추상화 자격이 생깁니다. 성급한 추상화는 그게 대체한 중복보다 삭제하기 더 어렵습니다.

추상화를 더하기 전에 제가 적용하는 시험은 이겁니다. *석 달 뒤 이 기능을 지운다면, 파일 몇 개를
건드려야 하나?* 답이 "하나, 그리고 그게 바로 이 파일"이면 좋습니다. 답이 "아홉 개, 공유 헬퍼 여기저기
흩어져 있음"이면 그 추상화는 자산이 아니라 부채입니다.

**이게 안 맞을 때:** 정말로 안정적이고 널리 공유되는 primitive(돈 타입, 날짜 util 같은 것)는 제자리
확장을 *의도한* 것이고, rule of three는 이미 한참 지났습니다. 명백히 추상화 자격을 얻은 코드의 네
번째 복사본을 정당화하려고 "삭제 기준 최적화"를 끌어다 쓰지 마세요.

## 4. 구현보다 의도

이름·테스트·주석은 **왜**를 실어 나릅니다. **어떻게**가 아니라요.

- **이름은 동작 방식이 아니라 의도를 담는다.** `itemList`가 아니라 `eligibleItems`. `processOrder`가
  아니라 `applyDiscount`. 읽는 쪽 — 사람이든, 새 세션의 에이전트든 — 은 본문을 읽지 않고 이름에서
  *이게 무엇을 위한 것인지*를 알 수 있어야 합니다.
- **테스트는 내부 호출이 아니라 관찰 가능한 동작을 검증한다.** "쿠폰을 적용하면 장바구니 합계가 10%
  줄어든다"를 확인하는 테스트는 리팩터를 견딥니다. "`applyCoupon`이 `recalculateTotals`를 한 번
  호출했다"를 확인하는 테스트는 동작이 똑같아도 내부를 재구성하는 순간 깨집니다. 구현에 결합된
  테스트는 **모든** 리팩터마다 복리로 불어나는 세금이 됩니다 — 에이전트가 거리낌 없이 리팩터하면 그
  세금은 쉴 새 없이 청구됩니다.
- **주석은 왜를 설명하고, 무엇을은 절대 설명하지 않는다.** `// 0으로 clamp: race 중 상류에서 재고가
  음수로 올 수 있음`은 제 몫을 합니다. `// i를 증가`는 아닙니다. 코드가 *무엇을*을 이미 말하고 있다면,
  그걸 반복하는 주석은 죽은 무게입니다. 주석은 제약, 우회책, 눈에 안 보이는 이유를 위해 아껴 두세요.

**이게 안 맞을 때:** 정말로 까다로운 동작 방식 — 비트를 만지는 hot loop, 미묘한 알고리즘 — 은 *어떻게*
주석이 있어야 할 때도 있습니다. 어떻게가 어려운 부분이니까요. 이 규칙이 금하는 건 필요한 설명이 아니라,
중복되는 "무엇을" 주석입니다.

## 5. 셋업 비용은 무제한, 태스크마다 드는 비용은 0

규칙을 자동화에 새겨넣는 **일회성 셋업**에는 얼마든지 쓰되, 그 규칙을 지키는 데 드는 **태스크당 비용**은
0을 요구하세요.

어떤 규칙을 도구 — lint, typecheck, formatter, test, CI gate — 로 강제할 수 있다면, **반드시** 그렇게
합니다. 문서에만 사는 규칙은 마감에 쫓기면 건너뛰게 되는 규칙입니다. 이건 앞의 분산 논리에서 곧장
따라옵니다. 셋업은 한 번 내지만 태스크당 준수 비용은 영원히 내므로, 모든 규칙을 벽(wall) 안으로 밀어
넣으세요.

따름 정리 둘:

- **모든 의존성은 부채다.** 하나를 더하기 전에, 왜 직접 짜지 않는지를 정당화하세요. 지루하고 잘
  이해된 기술이 기본값입니다. 새 의존성은 그걸 떠안는 비용에 맞서 제 자리를 스스로 벌어야 합니다.
- **저자가 AI라면 벽이 힌트를 이긴다.** 힌트 — 저자가 읽어주기를 기대하는 rules 파일 — 는 저자가
  기억하고 drift에서 스스로 회복하는 데 기댑니다. 에이전트에게는 회복할 근육 기억이 없으니, *벽*(hook,
  gate, 빌드를 실패시키는 lint 규칙)이 힌트보다 확실히 더 믿을 만합니다. 규칙은 *조언하는* 자리가
  아니라 *막는* 자리에 새기세요.

**이게 안 맞을 때:** 이번 주를 넘기지 못할 코드에 CI 파이프라인을 세우지 마세요. 셋업-비용-무제한
계산은 코드에 비용을 분산할 미래가 있다는 걸 전제합니다. 일회성 스파이크나 스크래치 프로토타입에는
그 미래가 없어서 자동화가 본전을 못 뽑습니다. 벽은 코드의 기대 수명에 맞추세요.

## 다섯을 관통하는 한 줄

각 원칙에 "이게 안 맞을 때" 경계가 붙은 건 일부러입니다 — 조건 없이 적용하는 원칙은 미신이 된
원칙이니까요. 다만 관통하는 한 줄이 있습니다. **비용을 한 번에 치를 자리로 밀어라.** 검증은 경계로(한
번 파싱하면 영원히 신뢰). 불가능한 상태는 존재 밖으로(표현 불가능하니 방어할 일도 없음). 확장보다
삭제로(영원히 유지하는 대신 싸게 재작성). 의도는 이름 안으로(매번 되유추하지 않고 읽는 순간 이해).
규칙은 벽 안으로(매 태스크 기억하지 않고 한 번 강제). 설계 결정이 자의적으로 느껴질 때는, 더 따지기
전에 이 다섯 중 하나가 그걸 정리해주는지부터 확인하세요.

## 요약

- **경계가 지저분함을 떠안는다** — 외부 입력을 가장자리에서 한 번 파싱해 branded 타입으로 만든다.
  코어는 순수하고 재검증하지 않는다. 신뢰 가능한 일회성 스크립트에는 생략.
- **불가능한 상태는 표현 자체를 막는다** — 플래그 뭉치보다 discriminated union, 코어에서는 예외보다
  `Result`. *안정화된* 코어에 적용하고, 아직 바뀌는 상태 기계는 느슨하게 둔다.
- **삭제를 기준으로 최적화한다** — "삭제하기 쉬움"이 "확장하기 쉬움"을 이긴다. Delete > Abstract >
  Duplicate > Generalize. 추상화 전 복사본 둘. "석 달 뒤 이걸 지우려면 파일 몇 개?"를 물어라.
- **구현보다 의도** — 이름·테스트·주석은 *왜*를 담는다. 테스트는 내부 호출이 아니라 동작을 검증하고,
  주석은 왜를 설명할 뿐 무엇을은 설명하지 않는다.
- **셋업 비용은 무제한, 태스크마다 드는 비용은 0** — 강제 가능한 규칙은 전부 도구에 새긴다. AI가 코드를
  쓰면 벽(hook·gate·lint)이 힌트(rules 파일)를 이긴다. 저자에게 근육 기억이 없으니까. 이번 주를
  넘기지 못할 코드에는 자동화를 생략한다.
